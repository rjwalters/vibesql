# VibeSQL Web Demo Redesign

## Executive Summary

Redesign the web demo to be a **performance storytelling platform** that communicates how VibeSQL is evolving over time. The primary goal is showing progress and stability, with competitive comparisons as supporting context.

## Current State

### What We Have
- **Interactive SQL Demo** (`index.html`) - Working well, keep as-is
- **Benchmarks Page** (`benchmarks.html`) - Point-in-time comparison chart
- **Conformance Page** (`conformance.html`) - Static pass rate display
- **Data Source**: Static JSON files generated by CI

### What's Missing
- No historical data (each deploy overwrites previous)
- No trend visualization
- No regression/improvement detection
- No connection to our rich database tracking

## Proposed Architecture

### Page Structure

```
/vibesql/
├── index.html          # Interactive SQL Demo (keep as-is)
├── performance.html    # NEW: Performance Dashboard (replaces benchmarks.html)
└── conformance.html    # Redesigned: Test Conformance Dashboard
```

### Data Flow

```
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────┐
│  Benchmark DB   │────▶│  generate_dashboard  │────▶│  dashboard.json │
│  (~/.vibesql/)  │     │  (Python script)     │     │  (web-demo/)    │
└─────────────────┘     └──────────────────────┘     └─────────────────┘
                                  │
                                  ▼
                        ┌──────────────────────┐
                        │  Previous dashboard  │
                        │  (from GitHub Pages) │
                        └──────────────────────┘
```

**Key insight**: Each CI run downloads the previous `dashboard.json` from GitHub Pages, appends the new data point, and re-uploads. This gives us historical data without needing external storage.

## Implementation Plan

### Phase 1: Data Generation Script
**File**: `scripts/generate_web_dashboard.py`

1. Read from SQLite database (`~/.vibesql/test_results/`)
2. Query benchmark_runs, benchmark_results, tpcc_results, etc.
3. Download previous dashboard.json from GitHub Pages
4. Merge new data point into timeline
5. Compute aggregations (geo mean, trends, etc.)
6. Detect changes (improvements/regressions)
7. Output new dashboard.json

### Phase 2: Performance Page
**File**: `web-demo/src/performance.ts`

1. Hero cards with key metrics
2. Timeline chart (Chart.js line chart)
3. Tabbed benchmark suite display
4. Query detail table with sparklines
5. Changes feed

### Phase 3: Conformance Page Update
**File**: `web-demo/src/conformance.ts`

1. Update to use new dashboard.json format
2. Add timeline visualization
3. Improve category breakdown display

### Phase 4: CI/CD Integration
**File**: `.github/workflows/deploy-pages.yml`

1. Add step to generate dashboard data
2. Download previous dashboard from Pages
3. Merge and upload new version

## Technical Decisions

### Why Pre-aggregated JSON?
- Fast page loads (no client-side computation)
- Bounded file size (~50-100KB)
- Simple deployment (static files only)
- Works with GitHub Pages

### Why Not SQLite in Browser?
- Adds 500KB+ to page weight
- More complex build process
- Overkill for visualization needs
- Current data fits nicely in JSON

### Data Retention Policy
- **Daily data**: Keep 90 days
- **Weekly aggregates**: Keep 1 year
- **Monthly aggregates**: Keep forever
- **Total file size target**: <100KB

### Chart Library
- **Keep Chart.js**: Already in use, supports line charts, good for our needs
- **Add**: Time series axis, annotations, sparklines (via chart.js plugins)

## Success Metrics

1. **Page Load Time**: <2s on 3G
2. **Data Freshness**: Updated within 1 hour of CI completion
3. **Historical Depth**: At least 30 days of trend data
4. **Regression Detection**: Automatic flagging of >10% slowdowns
